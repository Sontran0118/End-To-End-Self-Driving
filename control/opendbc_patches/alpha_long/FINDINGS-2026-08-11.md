# Mazda alpha long on the CX-5 2023: why it does not engage

Written 2026-08-11, after a full evening of on-car testing. Read this before
changing anything in `opendbc/car/mazda/longitudinal.py` or trying another
configuration permutation — most of the obvious ones have now been tried and
measured, and the results are below.

## The headline

**Nothing is running the ACC state machine once the radar is muted.** Alpha long
mutes the radar and replays two of its three longitudinal outputs. The third —
`0x21F CRZ_EVENTS`, which carries the set speed — is not replayed at all.

Measured from a passive capture with the radar alive:

```
0x21b CRZ_INFO    50.0 Hz     replaced by us
0x21c CRZ_CTRL    50.0 Hz     replaced by us
0x21F CRZ_EVENTS  50.0 Hz     NOT replaced
```

Same rate. `0x21F` is not in `RADAR_IDS` and not in `LONG_ADDRS`; no code path in
this port has ever transmitted it.

The symptom: with the radar muted, pressing SET does nothing at all.
`setspd raw=100` across all 214 samples of the run. With the radar alive, the
same press moved it to `raw=15224` (75.6 kph).

### CORRECTION 2026-08-12: "0x21F vanishes" was never measured

The first version of this document said `0x21F` *vanishes under suppression* and
built the rest of its argument on that. **That claim did not follow from the
evidence it cited, and it is still unproven in either direction.**

`CarStateFromCAN.set_speed_raw` (`control_stack/dashcam.py`) is a **latch**. It
is initialised to `-1` and updated on every `0x21F`, and it is never invalidated
when the frame stops arriving. So a frozen `raw=100` is exactly what you see
whether `0x21F` stopped or is still arriving unchanged — the value alone cannot
distinguish them. The `raw=-1` runs (`d_p.asleep*.log`) are the ones where the
car was asleep from the start and the field never latched at all, which is why
`-1` looked like it meant "absent now". It means "absent since startup".

The frozen set speed does still prove something real, and it is the part worth
keeping: **the SET press is not being validated by anything.** Whatever computes
the set speed is not running. Whether that is because `0x21F` is gone, or
because its sender is still transmitting an idle frame it never updates, changes
which fix is correct — synthesising `0x21F` and owning the state machine, versus
using a suppression that leaves the radar's HMI half alive the way the upstream
port does.

**Instrumentation added 2026-08-12 to settle it in one bench run:**
- `setspd ... age=` on the `CAR` line — seconds since the last `0x21F`, `-1` for
  never. An age that climbs past ~0.1 s means the 50 Hz frame has stopped.
- a `CENSUS` line once per second while alpha long is armed — per-address bus-0
  rates for `0x21b 0x21c 0x21F 0x165 0x09d 0x361-0x366 0x499`, with our own
  transmits subtracted (the census counts the echo of everything we send, which
  is why a raw count of `0x21b` says nothing). `0x21F` is the one to read first:
  nothing in this port has ever transmitted it, so its rate there is the car's
  alone.
- `radar suppression: mode=` at the arm site — every `d_p.*.log` before this is
  unattributable, because `OP_RADAR_SUPPRESS` selects between two very different
  routes and nothing recorded which one ran.

Run it both ways before concluding anything further. See "Next".

This is consistent with every other measurement of the evening: our frames are
correct, the panda permits them, the bus ACKs them, `long_tx_err` is 0, and the
car does nothing. Including a commanded `+2.00 m/s^2` from a standstill, which
left the engine at idle 646 rpm with no gas and no brake.

`acc_active=1` appears 769 times across every log this port has ever produced.
All 769 have the radar transmitting. Not once from our own frames.

### What this implies

Either the PCM obeys a state machine we removed, in which case reproducing
longitudinal here means implementing it ourselves — synthesising `0x21F`,
tracking SET/RES presses to maintain our own set speed, and driving the
activation transition — or our suppression is simply harder than the one the
working community port uses, and the radar's HMI half is meant to survive it.

The upstream port (opendbc PR #3355, `yummydirtx`) is evidence for the second
reading: it **never replays `0x21F`**, still reads `cruiseState.speed` from it,
keeps `ret.pcmCruise = True`, and reports on-car engagement. That combination is
only coherent if, under *their* suppression, the radar keeps sending `0x21F` and
keeps deciding when ACC turns on. Their suppression is the **programming
session**; this port's default is the gentler-looking `0x28` standby ladder,
which was added later to keep communication DTCs off the cluster and which
disables the radar's transmit outright.

So the A/B in "Next" comes first. Only if `0x21F` dies under *both* routes is the
synthesis work the right answer, and only then is `ret.pcmCruise = True` wrong.

## Fixed this session (keep these)

**`0x21c` redundancy quad.** `MSG_1` / `MSG_1_INV` / `MSG_1_COPY` /
`MSG_1_INV_COPY` is a bit plus its inverse, duplicated — the shape a receiver
uses to reject a corrupted frame. Captured from the car across a stock ACC
activation, the radar sends `MSG_1=1` and `MSG_1_INV=1` on all 1903 non-zero
frames, in every state:

```
03 00 01 00 00 01 00 00  n=1502  MAIN off
03 00 13 00 00 01 00 00  n=130   MAIN on, ready
0b 00 13 00 00 01 10 00  n=72    ENGAGED
```

The upstream `CRZ_CTRL_TEMPLATES` carry `MSG_1=0` with `MSG_1_INV_COPY=1` — the
inverse on both halves — so every frame this port ever sent failed that check.
Now asserted at the end of `build_crz_ctrl` so no template or branch can
reintroduce it. **Still unverified on the car**: the drive ended before a SET
press could be tried under conditions where it could have mattered, and the
finding above suggests the quad alone would not have been sufficient anyway.

**Panda safety-param watchdog** (`dashcam_web.py`). It re-asserted the safety
mode with a hardcoded param `0`, clearing `MAZDA_PARAM_LONGITUDINAL` and
silently switching the firmware back to the 3-entry stock tx table — while
`can_send` kept succeeding and `long_tx_frames` kept climbing. It also never
checked `_h[13]` at all. Now repairs both mode and param, and the arm path reads
the config back and prints it. Fires on any board reset, including the cranking
brownout.

**`enter_radar_standby` restored.** Restoring the pristine vendored module had
removed it, so `interface.py`'s guarded import fell back to `"programming"` —
the heaviest tool in ISO 14229. To every other module an ECU in a programming
session is one being reflashed, so the camera, cluster and PCM each log a
communication DTC and the cluster reports *malfunction* rather than
*unavailable*. Standby (`28 81 01`) lands in ~0.38 s and leaves the radar
present and answering diagnostics.

**Web cruise readout.** Under alpha long the page showed `ENGAGED` off
`cruise_enabled`, which decodes from `0x21c` — our own muted frame — and had
been frozen at 1 since suppression. 175/175 samples read the self-contradictory
`crz_avail=0 crz_en=1`. Now uses the PEDALS-derived pair and labels the source.

**Module restored to `c94780cb`** (derive `0x21c` from the radar's observed frame)
with the quad fix applied on top. `carcontroller.py` matched to it; the
go-no-malfunction version is kept at `carcontroller.py.gonomal`.

## Tried and eliminated

Each of these was a hypothesis that survived reasoning and died on the car:

- frame content, checksums, counters — verified correct by DBC decode
- bus coverage (bus 0 only vs bus 0 + bus 2)
- suppression method: programming session vs `28 81 01` standby
- session type, DTC state, radar DTC clearing
- synthetic SET button press on `0x09D` — fired 3 times, no response
- engagement ordering: assert `ACC_ACTIVE` on MAIN vs wait for the PCM
- replaying the radar's own captured frames instead of templates — this also
  *caused* an FSB fault, because a frozen snapshot (`age=113.7s`) asserts
  something false to a camera that cross-checks against its own vision
- launch order / tx regularity as a camera-fault cause: the cleanest run of the
  night (worst txgap 28 ms vs 31–39 ms on runs with no fault) still faulted

## Dash faults: three causes, not one

These get conflated in the run notes. They have different mechanisms, different
owners, and only one of them is ours to fix.

**1. Smart City Brake Support / FSB / FCW / AEB — inherent, not a bug.**
The radar *is* those functions. It cannot command them if it cannot transmit, so
suppressing it removes them by definition, whichever route is used to suppress
it. Upstream's merge bar explicitly allows faults "expected from removing factory
FCW or AEB", and the community thread reports the same malfunctions as the
accepted cost. No configuration removes this while the radar is muted. Camera-
based low-speed SCBS survives.

**2. Communication DTCs from the programming session — a cost of the route.**
To every other module on the bus, an ECU in a programming session is one being
*reflashed*: it stops answering normal requests, so the camera, cluster and PCM
each log their own communication DTC against it and the cluster reports
*malfunction* rather than *unavailable*. That is what `enter_radar_standby` was
written to avoid. It is a property of how the radar was silenced, not of
silencing it — and it is precisely the trade the "Next" A/B has to measure,
because the route that raises these DTCs may also be the only one the car will
still engage under.

**3. Front camera sensor system — ours.** Two established causes, both in the
logs:

- **Frozen shadow replay.** A snapshot replayed at `age=113.7 s` asserts
  something false to a camera that cross-checks against its own vision — a lead
  that never moves is exactly the implausibility a fusion check exists to catch.
  `radar_shadow_thread` now **expires** dynamic frames (`OP_SHADOW_MAX_AGE_S`,
  default 20 s) and keeps replaying only `0x366`/`0x499`, the two the DBC defines
  no varying signals for. Letting a dynamic frame expire brings this fault back;
  that is the correct trade, because the fault is honest about the radar being
  gone where a frozen lead is a false statement about the road.
- **The CAN1 wedge.** bxCAN stuck in init stops cam↔car forwarding while
  `bus_off/txe/rxe` all read healthy, and the cluster raises a front camera
  sensor fault that looks identical to the alpha-long one. Watch `can rx=` on the
  `CAR` line, not the error counters. Already covered by the `0xd8` recovery.

Note also that the `RADAR` diagnostic line's `age=` is time since that address
was last seen *on the bus*, which once the replay is running is **our own echo**.
A healthy replay pins it near zero and says nothing about whether the radar is
back. Use the `CENSUS` line for that.

## RESULTS 2026-08-12: the A/B ran, on the car, parked

Three armed runs with the census and button counters live. Logs:
`drivelogs/ab_programming.log`, `ab_standby.log`, `ab_stdby_template.log`, plus
the two read-only references `census_baseline.log` and `census_acc_engaged.log`.

**1. `0x21F` does NOT vanish under suppression.** It holds 50 Hz through both
routes, for every second of every run, while the radar's nine frames all go to 0:

```
                     21b  21c  21f  165  09d  361..499
radar alive (ref)     50   50   50  100   10   10 each
programming            0    0   50  100   10    0
standby                0    0   50  100   10    0
```

So `0x21F` comes from whatever also sends `0x165 PEDALS` -- the PCM -- and the
headline of this document was wrong about the mechanism. **Do not synthesise
`0x21F`**: the PCM is already sending it and a second sender would collide.

**The conclusion survives the correction, though.** The set speed still never
moves and ACC still never activates, so the *decision* really does die with the
radar. The PCM keeps publishing the HMI frame; it just never computes anything to
put in it. State machine in the radar, display frame from the PCM.

**2. The SET press reaches the bus and nothing acts on it.** With the button
counters added, run 3 recorded `btn SET- 2 -> 14` -- fourteen clean rising edges
on `0x09d` -- while `setspd` stayed at raw=100 and `acc_active` stayed 0 for the
full 100 s. This is the measurement the earlier runs could not make, and it rules
out "the press never happened".

**3. The suppression route does not matter.** Same nine frames silenced, same
non-engagement, and -- MEASURED -- the same forward-sensing faults (FSM / FSBM)
on the cluster under BOTH. The rationale for `enter_radar_standby` was that it
would keep those faults off the dash. It does not. See the corrected note in
`interface.py`.

**4. `CRZ_INFO_STANDBY_TEMPLATE` was missing, and is now back.** `LONGDIFF` at
the transmit point, radar vs ours, same instant:

```
radar = 01 ff e3 ff c0 80 08 d5     idle: "no request"
ours  = 01 ff e2 00 04 80 00 99     ACCEL_CMD encoded as exactly 0.0
```

Bytes 0-5 of the radar's idle frame ARE the standby template that the 2026-08-11
revert deleted. Since that revert the port had been announcing a live zero
command in every not-engaged frame it sent. Restored in `longitudinal.py`, and
`build_crz_info` now returns the idle frame byte-for-byte when `not long_active`.
It did not produce engagement, but it removes a real and unnecessary difference.

**5. Two things validated for free.** `_compute_inverted_sum_checksum`
reproduces the radar's own checksum byte exactly (`sum(0..6)&0xff = 0x2a`,
`0xff-0x2a = 0xd5`) -- the first time that formula has been checked against
hardware rather than assumed. And `CRZ_EVENTS.CRZ_SPEED` is **km/h**: with stock
MRCC engaged, raw=14582 reads 72.4 km/h or 260.7 as m/s-converted, and no CX-5
has a 260 km/h set speed.

**6. Still open: `MYSTERY_BIT` varies.** Byte 5 bit 7 of the radar's idle frame
was `0x80` in one capture and `0x00` in the next, so no hardcoded template tracks
it. The fix is `set_observed_crz_info()` -- which `dashcam_web.py:2188` already
calls inside a bare `except: pass` and which **does not exist** in
`longitudinal.py`. That is why `0x21c` now matches the radar byte-for-byte and
`0x21b` never has: one observed-frame path is live, the other is silently dead.

### What is left, after all of that

Every configuration tried across two evenings sits inside one deadlock.
`ret.pcmCruise = True` means openpilot asserts `ACC_ACTIVE=1` only once the PCM
reports engaged; the PCM reports engaged only once something tells it to; that
something was the radar. Nobody moves first.

Breaking it means openpilot owns engagement: `pcmCruise = False`, engage on the
SET edge that run 3 proves is visible on `0x09d`, and assert `ACC_ACTIVE`
unprompted. That also needs the panda, because `mazda_tx_hook` gates `CRZ_CTRL`
with `CRZ_ACTIVE=1` on `controls_allowed`, and `controls_allowed` comes from
`pcm_cruise_check()` on PEDALS -- which by the above will never fire. So it is a
safety change and a reflash, in the shape other brands already use for
button-driven engagement.

That is a real scope step, not another permutation. Scope it before writing it.
